What the clinical literature says

Repetition is how motor automaticity is built. It is how a gestalt processor speaks. It is self-regulation. Only one of its four causes is a mistake.

= neutral polarity group: communication style

“Trying to reduce or stop repetitive tapping leads to less overall communication.”

AssistiveWare, /repeated-button-tapping → constraint C1 → metrics_catalog.polarity = 'neutral'

So the ban lives in the database, not in the copy. A neutral metric cannot be rendered in a warning colour, because the UI reads its polarity from the catalogue. Stimming does not get a red badge.

"We specified this ourselves, and we specified it wrong. Repeated tapping looked exactly like an error rate."

Why the rules are SQL and not a model

A speech therapist has to be able to disagree with a finding and trace the disagreement to a number. Every rule ships its thresholds and the exact rows that triggered it.

Routing is by data class, not by availability

utterance text, per-child patternslocal only
aggregates, counts, rateseither
the 8 diagnostic rulesno model at all

write_insight requires the fired_rule_id that justified it. No model prose reaches a teacher without SQL behind it.

"SQL decides what's true. The model only turns a fired rule into a sentence a teacher can read. And neither of them can reach what the child said."

  • Trace the flow left to right once with your hand. Don't narrate every box.
  • The two lines that matter: "rules are SQL so a therapist can argue with a number" and "write_insight requires a fired_rule_id."
  • If asked why Gemma and not a frontier model: it runs on a separate box we control, it costs nothing per night, and the sensitive data never leaves. Cloud gets sanitised concepts only.

Safety as a build gate

Advice a model cannot give, enforced four ways

layer 1

Catalogue

insights_catalog.forbidden_actions — a column on every rule.

layer 2

In-band

The list travels inside every MCP payload, so the model is told in the same breath as the evidence.

layer 3

Write gate

write_insight rejects reasoning text containing a forbidden action.

layer 4

CI

tools/verify.py fails the build. 42 checks, run on every build.

What the gate actually asserts

PASS no insight recommends reducing repetition
PASS no insight recommends relocating a learned button
PASS a refusal is never routed to retraining
PASS every AI mode is a filtered view of the robust board
PASS never proposes removing a core or essential word
PASS control child triggers no intervention
PASS all 8 rules fire on plausible data
PASS no value published below its min_n
WARN 4 known gaps in seed data, named

"Four layers, and the last one is a build gate. If someone writes a rule next month that recommends shrinking a grid, the build goes red."

  • Emphasise "a refusal is never routed to retraining" — if a child says no to something, drilling them to request it teaches them their no doesn't count.
  • Also worth saying: "all 8 rules must fire on plausible data". A rule that never fires is a comment.
  • The WARN is deliberate and named — three metrics need events the kids app doesn't emit yet. Slide 13.
Privacy · docs/mcp-api.md §10

“Read-only” was harder than it looks

Finding 1 — mode=ro cannot open a WAL database

A WAL reader must map the -shm file, which a read-only handle can't create. WAL is mandatory here, so the obvious implementation is unavailable.

Finding 2 — query_only does not block ATTACH

Verified on SQLite 3.50.6. INSERT, DELETE, DROP all blocked. ATTACH allowed. One statement through the query escape hatch would have read every utterance a child ever produced.

Three layers, weakest first

1SQL parse guard — SELECT/WITH only
fails to a parser bypass
2Deny-ATTACH authorizer at the VDBE
fails if not installed on that connection
3OS permissions — the MCP user cannot read the file
survives a full compromise of layers 1 and 2

Layer 3 is the one that makes the claim true. “Utterance text is unreachable” becomes a statement about the filesystem rather than about our code.

"We tried to open the database read-only. It doesn't work — a WAL reader has to write the shared-memory file. Then we found query_only doesn't block ATTACH."

  • The punchline: "one ATTACH through our own escape hatch would have read every utterance a child ever produced."
  • Then the fix: three layers, and only the third one is a real guarantee. "It's a statement about the filesystem, not about our code."
  • Both findings are verified against SQLite 3.50.6, not assumed. There's a CI check in the docs.
  • 5-minute cut: skip this slide — or keep just the ATTACH finding as one spoken sentence on slide 10.

What we have not built

Four things this does not do yet

No keyboard

Constraint C8 says a robust AAC system needs alphabet access from early learning. We have none. keyboard_use is defined in the schema so the gap is visible, not hidden.

The kids app is a shell

Data layer, rules, MCP server and verification all run. The PWA board and dashboard UI are next — the schema and the API contract are what we chose to get right first.

Three metrics have no events

suggestion_acceptance, vocabulary_gaps and visual_source_split need events the app doesn't emit yet. verify.py warns by name rather than passing quietly.

No clinician has reviewed this

The eight constraints come from AssistiveWare's published guidance, cited per constraint. That is reading, not review. A speech therapist signing off is step one, not step ten.

Offline is the honest one: a returning user on a warm cache is fine. A first visit with no network is not, and voice availability varies by browser. Flagged, not solved.

"Four things this doesn't do. I'd rather you hear them from me."

  • Frame the shell app as a choice, not a failure: "we got the contract right first, because the schema is the thing you can't refactor later."
